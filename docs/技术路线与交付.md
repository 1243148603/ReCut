## 1 起点：两份上游文档

| 文档 | 定义什么 |
|---|---|
| `204DEM切片与地形瓦片教程.md` | **怎么做**——命令行四步：下载 Copernicus 分幅 → gdalwarp 拼接裁剪 → ctb-tile 切片 → 手写 layer.json → 部署 |
| `PRD.md`（"Recut" V1.5） | **做成什么样**——Windows GUI 桌面软件，18 个 P0 功能需求、7 个非功能需求、9 条验收 |

问题是：这条链路全是命令行，依赖 Anaconda/GDAL/编译产物，步骤多、易错，
非命令行用户（交付人员）用不了。

**要交付的东西**：一个能双击安装、在界面上走完全流程的软件；
产物分两套——前端要的地形瓦片、算法侧要的裁剪数据。

## 2 技术路线

### 2.1 一句话

**C# 做界面与调度；拼接裁剪走 GDAL 的 C# 绑定；切片仍以子进程调用 ctb-tile。**

### 2.2 选型与理由

| 选择 | 为什么 | 代价 |
|---|---|---|
| **C# + .NET 8 + WinForms** | 目标平台只有 Windows（NFR-01/OUT-05）；WinForms 做"表单 + 队列 + 日志"这类界面最快 | 界面样式朴素 |
| **GDAL 走 C# 绑定**（`MaxRev.Gdal.Core`） | PRD §2 明确要求"用绑定而不是命令行"；绑定能在进程内拿到栅格元数据、做覆盖检查，不必解析文本输出 | 引入一个 native 依赖包 |
| **切片走 `ctb-tile.exe` 子进程** | CTB 没有可用的 C# 绑定；PRD §2 原文即"以子进程调用" | 要自己解析进度、处理取消 |
| **GDAL 版本钉死 3.13.3** | 基线的 Checksum 58775 是验收锚点。NuGet 上恰好有 `3.13.3.580`，与基线用的 conda GDAL 同版本号 → 不引入 warp 内核的版本偏移 | 升级该包必须重跑闸门 |
| **自包含发布** | NFR-02：用户机器不需要装 .NET / Anaconda / GDAL | 安装包 223 MB |
| **管理员权限不要** | 交付人员往往没有本机管理员权限 | 装到 `%LOCALAPPDATA%`，只对当前用户可见 |

### 2.3 分层

```
CutMap.App (WinForms)      界面：向导、队列、历史、设置
CutMap.Cli (控制台)        无界面诊断与回归——**所有验证靠它，不依赖窗口**
CutMap.Setup (WinForms)    安装程序（自研，见 §4.2）
      │
CutMap.Core                全部业务逻辑，**一行 UI 代码都没有**
      ├── Geo/        GDAL 封装：栅格摘要、拼接裁剪、覆盖检查
      ├── Terrain/    瓦片网格算术、切片编排、layer.json、算法元数据
      ├── Tools/      ctb-tile 子进程（进度、取消、失败检测）
      ├── Vector/     行政区划边界（加载、过滤、裁剪、导出）
      ├── Download/   分幅枚举、URL 模板、断点续传
      ├── Packaging/  打包与部署说明
      └── Store/      预设、历史、下载源、路径
```

**Core 不许依赖 UI** 不是为了好看：它让 `CutMap.Cli` 能在没有窗口的环境里跑完
所有验证。`.csproj` 里没有 `UseWindowsForms`，破了会编译不过。

## 3 实施路线

七个里程碑，**每一个都有可复跑的实测判据**，不是"看起来能用"。

| | 做什么 | 验收判据 | 结果 |
|---|---|---|---|
| **M0** | 环境与骨架；把"软件产物与命令行一致"这件事先钉死 | ① 30 幅拼接 Checksum = 基线 **58775**<br>② ctb-tile 失败能被检出 | ✅ |
| **M1** | 切片：进度、取消、参考层级、瓦片数护栏 | 切出 **223,495** 个瓦片，15 层逐层与基线相等 | ✅ |
| **M2** | 拼接裁剪：多选、覆盖拦截、算法元数据 json | Checksum 58775；json 与 tif 实测逐项一致 | ✅ |
| **M3** | 打包：layer.json、双产物、zip、部署说明 | 只前端/只算法/两套 三种组合都对 | ✅ |
| **M4** | DEM 下载：源可配置、断点续传、运行中暂停 | 30 幅枚举；URL 与教程逐字符相同；续传只取剩余 29.5 MB（整幅 44.2） | ✅ |
| **M5** | 行政区划：加载/过滤/矢量裁剪/随产物分发 | 真实重庆市边界，裙边四角同为 51.0 m；dissolve 6607→1900 顶点 | ✅ |
| **M6** | 队列/历史/预设/日志/许可/安装包/可加载性 | Cesium 逐级细分到 z14；瓦片解压 8452 字节 | ✅ |

### M0 为什么排在最前

因为它是**唯一能证伪整个技术路线**的一步。GDAL 绑定用的是 MaxRev 的构建，
与基线用的 conda 构建**不是同一份二进制**——如果两者的 warp 结果不一致，
后面所有"与命令行一致"的说法都不成立。

实测：**逐像素一致，Checksum 58775**。这条路才走得下去。

### 三个"做了但一开始是错的"

实施过程中有三处是**写完了才发现不对**的，都记在《开发与交接》里：

1. **`ctb-tile` 失败时退出码是 0**（源码里 `catch` 之后照样 `return 0`）。
   只看退出码会把坏瓦片当成功交付。现在以 stderr 判成败 + 瓦片数对账，
   并且用"缺坐标系的栅格"**实测复现**了这条路径。
2. **`dissolve` 一直是坏的**——`Union(null)` 抛异常被 `catch` 吞掉，
   静默退回几何集合。症状是"选了并集但产出里还带着内部界线"，不报错。
   改用 `UnaryUnion()` 后实测顶点减少 71.2%。
3. **中文文件名会在控制台断掉**——软件产出过 `重庆市_dem.tif`，
   ctb-tile 直接报 `could not open GDAL dataset`。改用行政区代码。

这三条都靠**一个会失败的判据**才发现，读代码看不出来。

## 4 交付物

### 4.1 软件

| | |
|---|---|
| 安装包 | `dist\CutMap-0.1.0-Setup-win-x64.exe`（223 MB） |
| 绿色版 | `dist\CutMap-0.1.0-win-x64.zip` |
| 运行要求 | Windows 10/11 x64。**不需要**装 .NET、Anaconda、GDAL |

两者都由 `cutmap/pack-*.ps1` 从源码一条命令重建，**不进仓库**（几百 MB 二进制）。

### 4.2 安装器为什么是自研的

PRD NFR-03 点名 Inno Setup，但本机拿不到：winget 装它要管理员提权（非交互环境
过不去），GitHub Releases 直连被墙（HTTP 000）。

于是自己写了一个（`cutmap/src/CutMap.Setup/`）。产出形态与 Inno Setup 一致：
双击安装、开始菜单与桌面快捷方式、在「应用和功能」里登记可卸载。
**额外的好处是免管理员**，反而更贴合"绿色版"的定位。

载荷用「追加」而不是嵌入资源——把 payload.zip 接在安装器 exe 字节后面，
再写一段定长尾部记录。这样打包脚本能只重跑拼接、不重编译安装器。

### 4.3 运行时依赖

`ctb/`（119 MB）——CTB 0.4.1 自包含分发包：4 个 exe + 49 个 DLL + GDAL/PROJ 支撑数据。
用 PE 导入表递归解析出最小 DLL 集，比教程的 `copy Library\bin\*.dll` 少约 570 MB。
**重建需要 VS2022 + conda**，所以直接入库。

### 4.4 数据

`resources/`（26 MB）——行政区划边界省 34 / 市 363 / 县 2840，附抓取脚本。
重新获取或换源：`python resources/fetch_boundaries.py`。

## 5 验收结论

### 5.1 关键行为

| 判据 | 结果 |
|---|---|
| 拼接裁剪与命令行一致 | Checksum **58775**、尺寸 17640×14760 |
| 切片与命令行一致 | **223,495** 个瓦片，15 层逐层相等 |
| 参考层级公式 | 4 组标定 15/14/13/12 全中 |
| `ctb-tile` 失败可检出 | 实测复现「抛异常却返回 0」 |
| 下载断点续传 | 截断到 1/3 后只取剩余 29.5 MB（整幅 44.2） |
| 下载 URL 模板 | 展开结果与教程 §3.1 那条**逐字符相同** |
| 双产物 | 只前端 / 只算法 / 两套 三种组合都对 |
| 按边界推导分幅 | 重庆：外接矩形 30 幅 → 真实相交 **21 幅**（省约 405 MB） |
| 矢量裁剪裙边 | 四角同为 51.0 m，切片后与源 DEM **差 0.0 m** |
| dissolve 取并集 | 合并 38 个区县 **6607 → 1900** 顶点 |
| 前端真能加载 | Cesium 逐级细分到 z14，瓦片解压 8452 字节 |
| 仓库自足 | 从零克隆 → 构建通过、闸门通过、打包依赖齐全 |

### 5.2 复跑方式

```bash
cd cutmap
dotnet run --project src/CutMap.Cli -- warp-gate    # 拼接 Checksum 58775
dotnet run --project src/CutMap.Cli -- ctb-gate     # 退出码陷阱实测复现
dotnet run --project src/CutMap.Cli -- grid-gate    # 15 层瓦片数 223,495
dotnet run --project src/CutMap.Cli -- boundary     # 边界加载/过滤/裁剪/dissolve
dotnet run --project src/CutMap.Cli -- verify <瓦片目录> <源DEM>
```

**改任何与瓦片网格或 GDAL 版本相关的代码后，跑 `grid-gate` 与 `warp-gate`。**
这两道闸门是"证明工具自己的输出对不对"，它们错了比功能错更难发现。

> `baseline/` 只保留了闸门要用的三个文件（瓦片数清单、标定结论、一个标定样本）。
> 其余的命令行脚本与证据留档已清理——命令行那一代实现已被软件取代。

## 6 与上游文档的三处偏离

| # | PRD/教程说的 | 实际做法 | 原因 |
|---|---|---|---|
| 1 | 教程的 6 处错误写法（`-m` 是层级、223,496 个瓦片、复制目录即可部署…） | 照基线实测值 | 基线逐条证伪过，见《基线运行说明》 |
| 2 | 行政区划数据来源：天地图 | **DataV.GeoAtlas** | 天地图 Key 已申请并实测，卡在它自己的权限类型判定（控制台显示服务器端、网关返回 301013 说浏览器端）。换源不改代码 |
| 3 | NFR-03：Inno Setup 安装包 | 自研安装器 | 本机拿不到该工具，产出形态一致，且免管理员 |

## 7 未做与后续

| 项 | 说明 |
|---|---|
| 干净机器验证 | 本机验过自包含与免提权；从零克隆验的是仓库自足，**不是** NFR-02 的跨机器可用性。这是交付前最该补的一条 |
| 断网切片 | 切片路径不依赖网络，但没专门断网跑过（PRD 验收 #5） |
| 切片耗时 | 重庆全域实测 527 s，教程写 3:21、基线记 354 s、PRD 写 3-4 分钟——四个数对不上。**硬件与版本完全相同**，差异是环境性的（最可能是杀软扫描 22 万个新建碎文件）。产物逐层与基线一致，不影响正确性 |
| 行政区划精度 | 现数据是简化版，边界位置偏差可达数百米。前端界线若用同一份数据绘制则完全吻合；要更高精度换数据源即可，不改代码 |
| GCJ-02 偏移 | 数据"声明 WGS84、实际是 GCJ-02"这类问题**查不出来**——偏移只有几百米，落在合法经纬度范围内。CRS 检查只能挡住投影坐标与缺少声明 |
| 并行任务 | PRD 列为 P2，当前串行 |
| 3D 预览 | PRD 的 OUT-02 明确不做；查看产物用 `serve.py` + `terrain_viewer.html` |
