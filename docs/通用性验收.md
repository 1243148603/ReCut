# CutMap 通用性验收

> **这份文档回答一个问题：换掉"重庆"这个案例，软件还能不能用？**
>
> 做法是拿非重庆的场景实测一遍，把结果逐条记下来——**能用的**与**断掉的**。
> 后面每一轮通用化改造，都对着这份记录验收；改完它要变成 `generality-gate` 闸门。

实测日期：2026-09-29。测试数据全部取自仓库现有的 30 幅 GLO-30 分幅，不依赖新数据源。

---

## 一、测试场景

| # | 场景 | 用什么 |
|---|---|---|
| ① | **非重庆区域**的完整流程 | 单幅 `N28_E105.tif`（105–106E / 28–29N，主体不在重庆） |
| ②a | 边界**超出** DEM 覆盖 | 泸州市（156510500，南边界 27.66N） |
| ②b | 边界**落在** DEM 覆盖内 | 南充市（156511300） |
| ③ | **投影坐标系**输入 | 把 `N28_E105.tif` 转成 `EPSG:32648`（UTM 48N） |

---

## 二、结果总览

**核心是通用的**——四件主要的事，三件在非重庆场景下完全正常：

| 环节 | 结果 |
|---|---|
| 切片（非重庆单幅） | ✅ 11,411 个瓦片，逐层与预期一致，17.7 s |
| 打包（非重庆） | ✅ layer.json 的 bounds 正确反推为 `[104.9963, 27.9932, 106.0071, 29.0039]` |
| 矢量裁剪（南充市） | ✅ 范围对齐、裙边四角同为 51.0 m、边界矢量随产物分发 |
| 覆盖检查（泸州市） | ✅ **正确拦下**："南边缺 0.3403°（约 37.6 km）" |
| 护栏（失控输入） | ✅ 拦下 1.2×10¹⁴ 个瓦片 |

**断掉的有 7 处**，分三类：验证手段写死、投影坐标系未识别、默认值引导。

## 三、断点清单

### A 类：验证手段写死（2 处）

#### A1 `verify` 的采样点是重庆四点

`cutmap/src/CutMap.Cli/VerifyCommand.cs` 的 `SamplePoints` 写死：

```csharp
("中部偏西", 107.75, 30.15), ("西北部", 106.25, 31.65),
("东北部", 109.45, 31.25), ("西南部", 105.55, 28.35),
```

对 `N28_E105` 的瓦片集，**3/4 落在范围外**，输出：

```
[--] 中部偏西 (107.75E 30.15N)：该点没有瓦片
[--] 西北部 (106.25E 31.65N)：该点没有瓦片
[--] 东北部 (109.45E 31.25N)：该点没有瓦片
```

不是错误，但**没有信息量**——它没说"这个瓦片集在哪"，只说"我找的那四个点不在"。

#### A2 `verify` 的 50 m 阈值对陡坡太紧

剩下那一点报 **113.4 m** 差异并判 FAIL：

```
[OK] 西南部 (105.55E 28.35N)：瓦片 311.0 m / 源 424.4 m / 差 -113.4 m
[!!] 最大高差在重采样噪声量级内（< 50 m）：实测最大 113.4 m
```

**查过了，是真实地形，不是数据错**：该点 DEM 周边 31×31 像素（约 930 m 见方）的高程范围是 **328.4 ~ 467.8 m，极差 139.4 m**。十几米的水平偏移在那种陡坡上就能造成上百米垂直差。

瓦片本身是对的（解码值 310.2 m，与源 DEM 在同一坡面上）。**是判据不合用**：单像素对单像素的比较，在陡坡上必然噪声很大。

### B 类：投影坐标系未识别（3 处）

#### B3 自动推层级 → 未处理异常 + C# 堆栈

```
输入：utm48n.tif
  3386×3830，EPSG:32648，像元 104526.734″      ← 米被当成度读了
  范围（GDAL 口径）：[499986.3, 3097208.2, 598299.5, 3208413.0]
  推导最深层级：-3
Unhandled exception. System.ArgumentOutOfRangeException: 层级不能为负
   at CutMap.Core.Terrain.CtbGrid.Estimate(...)
   ...
```

**用户看到的是 C# 堆栈**，而消息"层级不能为负"指不到真正的原因（投影坐标系）。

#### B4 显式给层级 → 被护栏拦下，但理由指不到点

```
FAIL  瓦片数 120,772,826,226,530 超过上限 2,000,000
```

拦住了，但"120 万亿个瓦片"会让用户去调层级或缩范围，**而真正该做的是把数据转成经纬度**。

#### B5 覆盖检查拿米比度

```
[!!] 西边缺 499866.6265°（约 49040265.3 km）。 南边缺 3097194.4907°（约 342469183.6 km）。
```

**这一条揭示了一个反直觉的事实**：拼接裁剪的**实际执行**对投影输入是能用的——`gdalwarp` 自己会重投影。坏的是**覆盖检查**，它把投影坐标当经纬度比，于是算出"缺 4904 万公里"。

> 所以「拒绝投影输入」不该一刀切地加在所有地方：**该拦的是会算错的环节（层级推导、覆盖检查），而不是能算对的环节（warp 本身）**。

### C 类：默认值与辅助工具写死（2 处）

#### C6 `terrain_viewer.html` 五处写死

| 位置 | 写死的东西 |
|---|---|
| `:59` | `TERRAIN_URL = './data/outputs/cesium_terrain/'` |
| `:60` | `WORLD_CENTER = { lon: 107.75, lat: 30.15 }` — 镜头中心 |
| `:61` | `MAXZOOM = 14` |
| `:95` | 4 个采样点，含期望高程（如 399.2） |
| `:241` | 自检项 `14/25968/10752` — **一个重庆专属的瓦片坐标** |

最后一条最隐蔽：换区域后它是**合法的 404**，但自检会报失败——**假报警比不报警更耗人**。

#### C7 四对话框默认值 + CLI 九处硬编码路径

- `DownloadForm:72` 默认区域 = 重庆矩形
- `MosaicForm:73` 默认套重庆预设
- `PresetForm:291` / `TaskPresetEditForm:185` 新建时以重庆为模板
- `CutMap.Cli/Program.cs` 有 9 处 `@"D:\Map"`

都能改，但每次都要改。

## 四、这份记录要变成什么

| 断点 | 归属批次 |
|---|---|
| B3 / B4 / B5 投影坐标系 | 批次 1（**优先**——现在是崩溃与费解的数字） |
| C6 预览页 | 批次 2 |
| C7 默认值 | 批次 3 |
| A1 / A2 verify 采样点与阈值 | 批次 5（固化成闸门时一并改） |

**回归底线**：批次 1–4 改完后，既有四条闸门（`grid-gate` / `warp-gate` / `ctb-gate` / `boundary`）必须仍然 PASS——那保证了"没有为了通用化而改坏了与基线的一致性"。

## 附：一处对原判断的修正

计划初稿里我写"投影坐标系**可能静默出错**"。**实测不会静默出错**——两条路径都被挡住了（自动层级靠崩溃、显式层级靠护栏）。

所以批次 1 的目标要改一改：不是"防止产出错误数据"，而是**把崩溃和费解的数字，变成一句能照着做的话**。
